## 二、关键发现清单

### 【中】N-1 标记删除即绕过 H-3 重置令牌门（r14 未涉的新 residual，未登记）

v2.17.0 H-3 的整个防御逻辑是：账本+锚双删但 `_read_marker()` 为真 → 弹 `FROZEN-RESET-BLOCKED` → 必须 `ALLOW_RESET=1` 且 `_RESET_TOKEN` 正确。

但 `_marker_path()`（freeze.py L218-220）返回的文件**从未 `_protect()` 落只读**——与锚点（0444 / READONLY）形成保护不对称。且 `_write_marker`/`_remove_marker` 不写 `_audit_log`，**标记删除完全无痕**。

推论（依磁盘源码 L220、L520-525 静态判定）：
```
有 HOME 写权攻击者：
  rm <anchor_dir>/<skill>.installed   # 无只读保护、无审计
  → marker 缺失 → _record_gate 判为"首次全新初始化"
  → 走 tokenless 初始化分支，H-3 的 _RESET_TOKEN 门根本不被评估
```
即 H-3 收口所依赖的前提「标记存在」**可由无令牌删除动作静默摧毁**。

诚实边界：这与 residual ①⑤（持锚写权 = 已破信任根）同处"跨信任根写权"边界，故非全新攻击类。但语料 §5 ①~⑧ **未点名"标记删除静默绕过重置门"这一具体状态转移**，且标记与锚点保护强度的不对称未在威胁模型登记。判读口径：tree-only 攻击者仍被 H-3 有效防御（不可写 HOME）；但 H-3 的防御力**等于标记文件的完整性**，此前提未登记。

### 【中】N-2 §4.1 仍是被引缺失证据文件，F-6 收口不彻底（新缺口）

§4.1「冻结清单重种子化 + verify 输出」正文仅为：

而 §1 F-6 收口陈述为「删除『被引证据文件在磁盘上』类声明；改为把运行输出全文内嵌……使证据随语料自足」。§4.1 同时违反"删除被引证据文件"与"证据自足"两项收口承诺。

与 r14 F-6 同性质但方向相反：F-6 是"引了不存在的文件"，N-2 是"明知文件缺失却仍以引用形式保留占位符"。**31/31 回归（§4.2）已自足证明回归，§4.1 的 reseed 证据实为冗余——应直接删除该小节，而非留缺失占位符。**

### 【中】N-3 复现命令对宿主环境敏感，照抄即崩

F-5 收口将 runner `PY` 改为 `sys.executable`，方向正确。但语料 §4.0 给出的复现命令是裸调：
```
C:\Users\Administrator\.workbuddy\binaries\python\versions\3.13.12\python.exe scripts/_run_all_tests.py
```
独立实测：**照抄此命令直接崩溃**，退出码 1，无 rc≠0 的测试结论——
```
Error in sitecustomize; set PYTHONVERBOSE for traceback:
AssertionError: SRE module mismatch
  File "...\cpython-3.11-windows-x86_64-none\Lib\re\_compiler.py", line 18
AssertionError: SRE module mismatch
```
根因：本机 shell 的 `PYTHONHOME=C:\Users\Administrator\AppData\Roaming\uv\python\cpython-3.11-...`（uv 3.11 stdlib），与 3.13.12 解释器混搭触发 stdlib 版本断言。**清空 `PYTHONHOME="" PYTHONPATH=""` 后同命令 31/31 逐行复现。**

判定：F-5 关于"解释器不兼容时套件自身 rc≠0 fail-loud"的承诺成立——但崩溃发生在**套件导入阶段之前**（`import glob` → `import re`），属解释器启动期失败，**runner 的 fail-loud 机制根本没机会运行**。故"复现命令随解释器一致"的承诺在宿主环境污染下**不可复现**。语料未声明任何环境前置（PYTHONHOME 隔离），审计员照抄必然失败。

### 【低】M-1 F-8 收口声称有，但 `test-freeze-appendonly.py` 未入语料

§1 F-8 收口陈述有实跑级断言，§2/§3a/§3b/§3c 均给出了逐字源码作为 F-9/F-10/F-4/F-5 的**代码层证据**。唯独 F-8 的承载文件未内嵌——F-8 的证据只能落到磁盘外部文件。虽与 §0.5 "证据随语料自足"精神一致的方向相反，但 F-8 本身是关于"测试锚点泄漏"的发现，其证据不在语料内属结构性例外（语料若内嵌该测试，则测试会污染自身）。判为低。**建议**：在 §0.5 增设 `test-freeze-appendonly.py` 的 sha256 登记行（源文件哈希即可，不必全文），使 F-8 证据链可就地锚定。

### 【低】M-2 审计日志 / 标记写入失败静默忽略，特权操作可无痕

`_audit_log`（L270-283）、`_write_marker`（L321-328）、`_remove_marker` 均 `except Exception: pass` 静默吞掉。锚点写失败是 fail-closed 的（`record()` L577-582 显式 `return -1`），但**审计日志与安装标记写失败不阻断**——特权操作（`anchor-init` OK、record OK）可能在**无任何审计轨迹**的情况下成功。与 N-1 叠加：攻击者若同时令审计目录不可写，标记删除与特权操作均无痕。

### 【低】M-3 过程性：自评收口未收敛（r7→r15 每轮新挖）

r14 已点过 F-6/F-7 同类病复发；本版 F-1/F-2/F-3 以 §0.5 自校验表根治（值得肯定），但 N-1/N-2 为 r14 未涉的新发现。**每轮收口都伴随新残留，说明"自评 F-1~F-10 全收口"的自评能力缺乏预测力**——这正是 r14 以"证据链自身"为阻塞主因的结构性理由的重演。此项不构成代码缺陷，但构成评级不可升级的理由。
